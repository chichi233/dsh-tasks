## 1. 两张图各回答什么问题

| 图 | 回答的问题 | 读法 |
| --- | --- | --- |
| `architecture.png` | **这套东西由哪些层组成、层与层之间谁依赖谁、地基坏了会波及什么** | 从下往上：外部 → 地基 → 能力 → 交互。地基每一格写了「谁读它 / 坏了会怎样 / 落点在哪」 |
| `hierarchy.png` | **点下去有几层、每一层读哪个库、加一个新模块要挂哪五个点** | 三件事一起看：① 点击深度（rail → B → C，三级封顶）② 数据归属（库名徽标）③ 挂载点（C 节五条） |

一句话分工：架构图答「坏了会怎样」，层级图答「加东西该插哪」。

## 2. 与 01 / 02 / 03 的区别

| 套 | 是什么 | 什么时候看它 |
| --- | --- | --- |
| `01-ticktick-original` | 竞品本体（滴答清单）的功能树 | 想知道「别人做到了什么」 |
| `02-plugin-current` | **当前已实现**的插件界面（两列模型，client.js 同一版本） | 想知道「我们现在有什么、点进去看到什么」 |
| `03-stage3-plan` | 第三阶段**功能计划**（绊脚石 / 禁止清单 / 必做之事 / 标签 / 蓝按钮 / 权重环 / 模块开关） | 想知道「接下来要做什么功能」 |
| `04-foundation`（本套） | **第四阶段的地基**：注册表 / 数据库 / 设置 / 主题 / 音效 / Agent 通道 | 想知道「做那些功能之前，必须先有什么」 |

四套的边界容易混，记这一条：**02 是现状、03 是功能清单、04 是支撑功能的地基**。02 里已实现的能力在 04 上层的 L2 原样出现（实线卡），03 的能力在 04 的 L2 里是灰底卡（只登记、本轮不实现），04 独有的是 L3 地基层的六件（虚线卡 = 本轮新增）。

## 4. 与 `stage4-foundation.md` §14 的两处偏差（登记，不是静默改动）

1. **§14.1 说「架构图上不要出现文件名」，本套的 L1–L3 卡片都带了 `file:line` 或「待建 5x」**。理由：本次验收明确要求「每格标出真实 `file:line` 或『待建（t5x）』」。两张要求冲突时我按验收执行，并把文件名压到每格最后一行、小字号，不参与主视线。若要回到 §14.1 的口径，删掉每格末行即可，`spec_foundation.py` 里每张卡的 `lines` 最后一条就是落点。
2. **§14.2 的层级图是「根节点 → 三层 → 12 能力 → 若干子功能」，本套的层级图按「点击深度 × 数据归属 + 挂载点」重排**。理由同上：验收要求画 rail→B→C 三级与五个挂载点。两种组织方式互补——§14.2 的组织适合回答「能力清单有多深」，本套适合回答「新模块插哪」；能力清单已在 `architecture.png` 的 L2 完整出现，所以层级图不再重复列 12 个能力节点。
